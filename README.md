# Finflow

Finflow - BNPL платформа (Buy Now Pay Later) которая позволяет клиенту оформить рассрочку на какой либо товар и платить потом.

Проект является демонстрационным для курса Highload Architect. В нем демонстрируется работа паттерна Saga в рамках бизнес-процесса оформления рассрочки

## Этапы

В рамках процесса оплаты система должна последовательно реализовать следующие шаги:
- Создать заявку на оформление рассрочки.
- Проверить и зарезервировать доступный кредитный лимит клиента.
- Создать финансовое обязательство перед магазином.
- Активировать договор рассрочки.
- В случае бизнес-ошибки выполнить компенсирующие операции.

Например, клиент покупает товар за 20 000 ₽, имея доступный лимит 50 000 ₽. При успешном оформлении рассрочки его доступный лимит становится равен 30 000 ₽. Если магазин отклоняет операцию, резерв снимается и лимит восстанавливается до 50 000 ₽.

## Границы MVP

Что нужно реализовать

- Оформление рассрочки
- Резервирование кредитного лимита
- Финансовое обязательство перед магазином
- Активацию договора
- Компенсирующие транзакции
- Историю выполнения SAGA
- Идемпотентность
- Нагрузочное тестирование

### ADR

Используется подход orchestration based saga тк в отличие от хореографии он позволяет явно показать состояние распределенной транзакции, последовательность шагов, обработку ошибок и компенсации транзакции.

Для демо варианта достаточно будет трех сервисов (Credit Limit Service, Merchant Service, Installment Service), одного экземпляра Postgres, RabbitMQ в качестве брокера.

### Installment Service

Основной сервис приложения, совмещающий публичное API и оркестратор SAGA.

Зона ответственности:
- Приём заявок на оформление рассрочки.
- Управление жизненным циклом заявки.
- Хранение состояния SAGA.
- Отправка команд другим микросервисам.
- Обработка результатов выполнения команд.
- Запуск компенсирующих транзакций.
- Активация договора рассрочки.
- Хранение истории выполнения SAGA.
На начальном этапе оркестратор не нужно выносить в отдельный микросервис.

### Credit Limit Service

Сервис управления кредитными лимитами клиентов.

| Операция | Описание |
| -------- | -------- |
| ReserveLimit | Резервирование необходимой суммы |
| ReleaseLimit | Освобождение зарезервированной суммы |
| GetLimit | Получение текущего состояния лимита |

Основная задача сервиса — гарантировать невозможность превышения кредитного лимита даже при одновременном поступлении множества заявок от одного клиента.

### Merchant Service

Сервис управления финансовыми обязательствами перед магазинами.

| Операция | Описание |
| -------- | -------- |
| CreateMerchantObligation | Создание обязательства выплатить магазину стоимость покупки |
| CancelMerchantObligation | Отмена ранее созданного обязательства |

Реальные денежные средства не переводятся. Финансовое обязательство представляет собой запись в базе данных со своим жизненным циклом.

Для воспроизведения ошибок достаточно создать два магазина: один всегда принимает операции, другой всегда отклоняет их.

### Почему RabbitMQ, а не Kafka?

В данном проекте обмен сообщениями преимущественно строится вокруг выполнения команд и получения результатов, а не вокруг хранения и повторного чтения огромного потока событий.

RabbitMQ хорошо подходит для этой модели благодаря подтверждениям обработки, маршрутизации сообщений, очередям повторных попыток и Dead Letter Queue.

Kafka тоже применима, но для демонстрационного проекта не даёт существенных преимуществ, оправдывающих дополнительную сложность.
